## 1. Аудит текущего состояния редактора (Current Editor Audit)

### 1.1. Результаты визуального аудита в браузере
В ходе аудита действующей страницы редактирования (`/admin/pages/[id]`) зафиксировано:
1. **Вид рабочей области (Холста)**: Холст не является визуальным (WYSIWYG). Вместо реального отображения компонентов страницы он представляет собой вертикальный список служебных карточек-аккордеонов (`SortableBlockItem`). Внутри раскрытой карточки администратор видит исключительно технические поля ввода: текстовые поля для HTML-строк (`contentUzHtml`, `contentRuHtml`), селекты и выпадающие списки.
2. **Оценка результата**: Чтобы увидеть, как страница выглядит на самом деле, администратор вынужден открывать предпросмотр в отдельной вкладке браузера (`/admin/pages/[id]/preview`). Редактирование «вслепую» снижает скорость работы и приводит к ошибкам верстки.
3. **Способ добавления блоков**: Клик по блоку в левой палитре (`PALETTE_BLOCKS`) производит простое добавление нового объекта в конец одномерного массива `blocks`. Прямое перетаскивание мыши из палитры в заданную позицию на холсте отсутствует.
4. **Возможности вложенности (Nesting)**: Блоки не могут вкладываться друг в друга. Структура представляет собой плоский 1D-список. Блок «Колонки» (`columns`) является фиксированным монолитом, содержащим только 2–3 текстовые ячейки с примитивными полями, но не способен вмещать в себя другие произвольные блоки (видео, таблицы, аккордеоны).
5. **Стилизация**: Полностью отсутствуют визуальные настройки отступов (padding/margin), фона секций, скруглений, границ и типографики. Блоки привязаны к стандартным жестким стилям.
6. **Схема хранения данных (`packages/shared/src/types/page-blocks.ts`)**: Хранит линейный массив `PageBlock { id, type, sortOrder, isVisible, config }`. В базе данных таблица `page_blocks` хранит плоские строки с `sort_order`.

## 2. Модель раскладки (12-Column Grid Layout Model)

### 2.1. Иерархия: Секции, Ряды, Ячейки и Блоки
Страница больше не является вертикальной стопкой полос на всю ширину экрана. Вводится строгая 12-колоночная адаптивная сетка:

```
Page (Страница)
 └── Section (Секция: фон, вертикальные отступы, максимальная ширина)
      └── Row (Строка 12-колоночной сетки)
           └── Cell (Ячейка / Колонка: colSpan от 3 до 12, min 3)
                └── Block (Один или несколько контентных блоков)
                     └── [Опционально] Container Block (Tabs / Accordion / Cards)
                          └── Nested Row (Вложенная строка, глубина <= 2)
```

1. **Section (Секция)**: Горизонтальный смысловой раздел страницы. Управляет фоном (токены), вертикальными отступами и шириной внутреннего контейнера (`prose`, `standard`, `wide`, `full`).
2. **Row (Строка)**: Контейнер 12-колоночной сетки CSS Grid / Flexbox. Содержит от 1 до 4 ячеек (`Cell`). Сумма `colSpan` всех ячеек в строке строго равна 12 (или <= 12 с автоматическим заполнением).
3. **Cell (Ячейка)**: Колонка с шириной от 3 до 12 колонок (допустимые значения `colSpan`: 3, 4, 6, 8, 9, 12; минимальный размер — 3 колонки, что гарантирует читаемость контента и предотвращает появление узких нечитаемых столбцов).
4. **Контейнерные блоки (Nesting)**: Блоки-контейнеры (`accordion`, `tabs`, `cards_grid`, `section_container`) могут содержать вложенные строки с валидированной максимальной глубиной **не более 2 уровней** (Page -> Section -> Cell -> Container Block -> Nested Row -> Nested Cell -> Leaf Block). Превышение глубины 2 блокируется валидатором для предотвращения падения производительности и нечитаемой верстки на мобильных экранах.

### 2.2. Пограничное перетаскивание (Edge-based Drop Targets)
При перетаскивании блока над существующим блоком или ячейкой область делится на активные зоны взаимодействия:
- **Левый край (0–20% ширины)** или **Правый край (80–100% ширины)**: Появляется вертикальный синий индикатор вставки. При отпускании текущая строка разделяется пополам или создается новая ячейка рядом (соседние `colSpan` пропорционально пересчитываются, например $12 \to 6+6$ или $6+6 \to 4+4+4$).
- **Верхний край (0–25% высоты)** или **Нижний край (75–100% высоты)**: Появляется горизонтальный индикатор вставки. Блок вставляется выше или ниже целевого блока внутри той же ячейки.
- **Межстрочный интервал (Gutter между рядами)**: Появляется горизонтальная разделительная линия на всю ширину секции. Отпускание создает новый ряд (`Row`) с одной ячейкой (`colSpan: 12`).

### 2.3. Изменение ширины колонок (Grid Snapping Resize)
- **Мышь**: Между ячейками отображается маркер изменения размера (Resize Splitter). При перетаскивании разделителя ширина обеих соседних ячеек плавно привязывается к 12-колоночной сетке (шаг в 1 колонку, допустимые пропорции: 3+9, 4+8, 6+6, 8+4, 9+3, 4+4+4, 3+6+3, 3+3+3+3).
- **Клавиатурная доступность (Обязательно)**: Каждая ячейка снабжена кнопками «Увеличить ширину (+1 колонка)» / «Уменьшить ширину (-1 колонка)» с немедленным речевым оповещением через `aria-live` («Ширина колонки изменена: 8 из 12»). Для каждого действия перетаскивания предусмотрены клавиатурные эквиваленты: «Переместить блок в соседнюю колонку», «Переместить выше/ниже», «Вынести в отдельную строку».

### 2.4. Запрет абсолютного позиционирования (No Absolute / Free Pixel Positioning)
Свободное перетаскивание элементов в абсолютных пикселях (`top: 142px; left: 380px`) **категорически запрещено** по следующим инженерным причинам:
1. **Разрушение адаптивности**: Экран смартфона (360–420px), планшета (768–1024px) и монитора (1920px) имеют разную ширину. Абсолютные координаты неизбежно приводят к обрезанию текста, горизонтальному скроллу и наложению блоков.
2. **Разрушение доступности (WCAG 1.3.2 Meaningful Sequence, WCAG 1.4.10 Reflow)**: При абсолютном позиционировании визуальный порядок полностью расходится с порядком DOM-дерева. Пользователи экранных дикторов и навигации клавишей `Tab` перескакивают по элементам хаотично.
3. **Двуязычность контента**: Текст на узбекском и русском языках имеет разную длину (разница до 20–40%). При фиксированных пикселях более длинный перевод перекрывает соседние кнопки и заголовки.

## 3. Правила адаптивности (Responsive Rules)

1. **Единство визуального и DOM-порядка**: Порядок ячеек в DOM-дереве обязан на 100% совпадать с визуальным порядком слева направо. Применение CSS-свойств `order: -1`, `order: 2` или `flex-direction: row-reverse` запрещено.
2. **Планшеты (Tablet, 768px – 1023px)**:
   - Ячейки с `colSpan >= 6` сохраняют пропорции.
   - Четыре колонки ($3+3+3+3$) автоматически группируются в сетку $2 \times 2$ (по 6 колонок каждая).
   - Три колонки ($4+4+4$) адаптируются в $12 + 6 + 6$ либо выстраиваются вертикально.
3. **Мобильные устройства (Mobile, < 768px)**:
   - Все ячейки автоматически разворачиваются на полную ширину (`colSpan: 12`) и выстраиваются вертикально строго в порядке их следования в строке.

## 4. Анализ библиотеки Drag-and-Drop (`dnd-kit`)

### 4.1. Официальные источники и возможности
- **Официальная документация**: [docs.dndkit.com](https://docs.dndkit.com) (Разделы: *Collision Detection Algorithms*, *Sensors / Keyboard*, *Droppable*)
- **Статус библиотеки**: Установлена в проекте (`@dnd-kit/core`, `@dnd-kit/sortable`, `@dnd-kit/utilities`), лицензия **MIT**, полная поддержка React 18 / Next.js 14.

### 4.2. Поддержка ключевых требований конструктора
1. **Определение зон падения по краям (Edge-based drop targets)**:
   - `dnd-kit` поддерживает встроенные алгоритмы `pointerWithin`, `rectIntersection`, `closestCorners`, а также создание **пользовательских алгоритмов коллизий** (`CollisionDetection`).
   - Функция коллизий получает точные координаты курсора (`pointerCoordinates`) и габариты контейнеров (`droppableRects`). Это позволяет с точностью до пикселя рассчитывать попадание в 20%-ные краевые зоны элементов (лево, право, верх, низ).
2. **Индикаторы зоны вставки (Drop Indicators)**:
   - Компонент `<DragOverlay>` в связке с хуками `useDroppable({ data: { edge: 'left' | 'right' | 'top' | 'bottom' } })` позволяет рендерить адаптивные полосы вставки в реальном времени без скачков макета.
3. **Клавиатурные сенсоры (Keyboard Sensors)**:
   - Сенсор `KeyboardSensor` с генератором координат `sortableKeyboardCoordinates` обеспечивает доступную навигацию с клавиатуры. Для сложных сеток он дополняется кастомными горячими клавишами (`Alt + ArrowLeft/Right` для переноса между ячейками).
4. **Вывод**: `@dnd-kit` полностью закрывает все потребности визуальной 12-колоночной сетки. Замена библиотеки не требуется.

| **Повторное использование** | Нет | **Библиотека сохраненных блоков (Patterns / Reusable Blocks)** |

## 6. Модель стилизации (Design Tokens & WCAG AA Enforcement)

### 6.1. Разрешенные дизайн-токены (Строгий отказ от произвольных цветов и CSS)
Администратору запрещено вводить произвольные HEX-коды (`#ff00ff`) или писать произвольный CSS. Выбор доступен исключительно из проектных дизайн-токенов:

1. **Цветовые стили фона секций и карточек**:
   - `default` (прозрачный / стандартный цвет фона страницы)
   - `subtle_muted` (мягкий нейтральный фон для чередования секций)
   - `card_surface` (фон карточки с тонкой рамкой и мягкой тенью)
   - `primary_tint` (светлый акцентный фон бренда: 5% насыщенности)
   - `primary_solid` (полная заливка акцентным цветом бренда учреждения)
   - `dark_contrast` (глубокий контрастный фон для футера или акцентных блоков)
2. **Шкала вертикальных отступов (Padding Scale)**:
   - `none` (0px)
   - `compact` (py-6 — 24px)
   - `normal` (py-12 — 48px) — значение по умолчанию
   - `relaxed` (py-20 — 80px)
3. **Межколонные промежутки (Gutter / Gap)**:
   - `compact` (gap-3 — 12px)
   - `normal` (gap-6 — 24px)
   - `wide` (gap-8 — 32px)
4. **Ограничитель ширины контейнера (Container Width)**:
   - `prose` (max-w-3xl — 768px) — оптимально для чтения положений и уставов
   - `standard` (max-w-5xl — 1024px) — типовые текстово-графические разделы
   - `wide` (max-w-7xl — 1280px) — многоколоночные сетки, каталоги, бенто-структуры
   - `full` (w-full px-4) — промо-экраны и панорамные баннеры
5. **Скругление углов (Border Radius)**:
   - `none` (0px), `sm` (4px), `md` (8px), `lg` (16px), `full` (pill)
6. **Выравнивание контента**:
   - `left` (по левому краю), `center` (по центру), `right` (по правому краю)

### 6.2. Автоматическая валидация контрастности WCAG 2.1 AA
При выборе комбинации цвета фона и цвета текста редактор вычисляет коэффициент контрастности по алгоритму относительной яркости W3C ($L_1 + 0.05 / L_2 + 0.05$):
- **Нормальный текст (< 24px)**: Требуемый коэффициент не менее **4.5:1**.
- **Крупный текст (>= 24px или полужирный >= 19px)**: Коэффициент не менее **3.0:1**.
- **Индикация в интерфейсе**: Если комбинация не проходит порог, отображается предупреждающий бейдж `WCAG AA: Недостаточный контраст (2.6:1)` и кнопка сохранения настроек стиля **блокируется** до выбора контрастного токена.

## 7. Библиотека блоков V2 (Новые и обновленные блоки)

Все блоки сгруппированы по функциональным категориям образовательного портала:

### 7.1. Структура и контейнеры (Layout & Containers)
1. `section_container` — Секция с выбором фона, ширины контейнера и отступов.
2. `cards_grid` — Сетка из 2–4 адаптивных карточек с иконками, бейджами и ссылками.
3. `tabs` — Вкладки с переключаемым содержимым (доступно с клавиатуры через `ArrowLeft/Right`, `role="tablist"`).
4. `accordion` — Раскрывающиеся секции (FAQ, перечни вопросов, правила приема).

### 7.2. Главные экраны и призывы (Hero & Banners)
5. `hero` — Академический главный экран страницы (заголовок, бейдж направления, подзаголовок, 1–2 кнопки действий, изображение или градиентный фон).
6. `banner_alert` — Официальное уведомление / предупреждение (информационное, важное, дедлайн, приказ).
7. `call_to_action` — Блок целевого действия (призыв подать документы, записаться на курсы, перейти в бот).
8. `quote` — Цитата руководства учреждения или выдающегося деятеля (текст, автор, должность, фотография).

### 7.3. Текст и медиа (Content & Media)
9. `heading` — Заголовок H1–H6 с семантической проверкой иерархии.
10. `rich_text` — Форматированный текст со списками, цитатами и ссылками.
11. `image_text` — Композиционный блок «Фотография + текст сбоку» (с переключением стороны: фото слева / фото справа).
12. `image_carousel` — Слайдер фотографий. **Обязательное требование доступности WCAG 2.2.2**: автопрокрутка по умолчанию отключена, обязательна видимая кнопка «Пауза / Воспроизведение», поддержка клавиатуры.
13. `media_gallery` — Адаптивная сетка фотографий с предпросмотром и всплывающим окном.
14. `video_embed` — Встраивание видео с YouTube, Vimeo, Mover.uz с валидацией белого списка доменов и доступным заголовком `title`.

### 7.4. Академические и динамические данные (Data & Widgets)
15. `stats_counter` — Блок статистических показателей (число студентов, педагогов, грантовых мест, % трудоустройства).
16. `timeline` — Хронологическая лента (исторические вехи техникума, этапы приемной кампании по датам).
17. `documents_list` — Реестр документов с иконками типов файлов (PDF, Word, Excel), номерами, датами и размером.
18. `staff_cards` — Карточки преподавателей и мастеров производственного обучения.
19. `specialties_feed` — Живой динамический каталог образовательных направлений техникума.
20. `events_feed` — Живой виджет предстоящих мероприятий и конференций.
21. `latest_news_feed` — Динамический виджет последних новостей с фильтром рубрик.
22. `schedule_widget` — Виджет расписания учебных групп.

### 7.5. Навигация и утилиты (Navigation & Utilities)
23. `anchor_nav` — Автоматическое оглавление страницы на основе заголовков H2/H3 с плавной прокруткой.
24. `social_links` — Блок ссылок на официальные верифицированные каналы (Telegram, YouTube, Facebook, Instagram).
25. `map_embed` — Интерактивная карта OpenStreetMap с метками учебных корпусов и общежития.
26. `button` — Индивидуальная кнопка-ссылка (primary, secondary, outline).
27. `divider_spacer` — Разделитель и настраиваемый отступ между блоками.

## 8. Вопрос форм обратной связи и заявок (Forms Analysis)

### 8.1. Правовой анализ законодательства Узбекистана
- **Источник**: [Закон РУз «О персональных данных» № ЗРУ-547 от 02.07.2019 (в ред. ЗРУ-1125)](https://lex.uz/docs/4396428), статьи 9, 10, 18, 27, 27-1. Статус: **VERIFIED**.
- **Ключевые требования к формам**:
  1. **Явное согласие (ст. 9, 18)**: Сбор ПДн (ФИО, телефон, адрес, паспортные данные, электронная почта) допускается исключительно при наличии информированного добровольного согласия субъекта. Чекбокс согласия не может быть предзаполнен. Обязательна прямая ссылка на Политику обработки персональных данных учреждения.
  2. **Локализация данных (ст. 27-1)**: Базы персональных данных граждан Республики Узбекистан должны физически храниться на серверах, расположенных на территории Узбекистана, с регистрацией базы данных в Государственном реестре.
  3. **Минимизация данных (ст. 10)**: Запрещено запрашивать избыточные данные, не соответствующие заявленной цели сбора.

### 8.2. Технические требования к формам
Создание произвольного «конструктора форм» в рамках данной фазы **не проектируется**, так как для безопасного функционирования требуются:
- Выделенная реляционная таблица `form_submissions` с шифрованием чувствительных полей;
- Механизм защиты от спама: капча (Cloudflare Turnstile) + строгий троттлинг IP-адресов;
- Модуль уведомлений ответственных сотрудников (Devonxona / Qabul komissiyasi) по почте и Telegram;
- Журнал согласий на обработку ПДн с фиксацией IP-адреса и временной метки.
- **Решение**: Проектирование произвольного конструктора форм выносится в отдельную самостоятельную фазу. На текущем этапе образовательный портал использует штатную проверенную форму контактов (`/contacts`) с обязательным чекбоксом согласия по ЗРУ-547.

## 9. Версионирование схемы и миграция данных (Schema Versioning & Zero Data Loss)

### 9.1. Структура версионирования
В объекте страницы вводится обязательное поле `schema_version`:
- `schema_version = 1`: Плоский список блоков первой версии (Phase S1–S3).
- `schema_version = 2`: Новая 12-колоночная иерархическая модель с секциями, рядами и ячейками.

### 9.2. Адаптер обратной совместимости (`migratePageBlocksV1toV2`)
Все существующие страницы техникума (включая 12 уставных страниц ст. 37 ЗРУ-637) сохраняют полную работоспособность без потери данных. При открытии страницы с `schema_version = 1` адаптер автоматически упаковывает каждый существующий блок в отдельную строку сетки:

```typescript
export function migratePageContentV1toV2(legacyBlocks: PageBlock[]): PageContentV2 {
  return {
    schemaVersion: 2,
    sections: [
      {
        id: 'section-migrated-root',
        style: { backgroundStyle: 'default', paddingVertical: 'normal', containerWidth: 'standard' },
        rows: legacyBlocks.map((block, index) => ({
          id: `row-migrated-${block.id || index}`,
          cells: [
            {
              id: `cell-migrated-${block.id || index}`,
              colSpan: 12, // Полноширинный охват
              blocks: [block],
            },
          ],
        })),
      },
    ],
  };
}
```
Публичный компонент `BlockRenderer` поддерживает обе версии: если получена версия 1, она мгновенно нормализуется адаптером в памяти без принудительной перезаписи БД.

## 10. Архитектурное решение по библиотекам (Library Decision)

### 10.1. Сравнительный анализ кандидатов

| Критерий | Кандидат А: Развитие текущего движка на `@dnd-kit` | Кандидат B: `@measured/puck` | Кандидат C: `@craftjs/core` | Кандидат D: GrapesJS / Builder.io |
|---|---|---|---|---|
| **Официальный сайт / Репо** | [docs.dndkit.com](https://docs.dndkit.com) | [puckeditor.com](https://puckeditor.com) | [craft.js.org](https://craft.js.org) | [grapesjs.com](https://grapesjs.com) |
| **Лицензия** | **MIT** | **MIT** | **MIT** | BSD-3-Clause / SaaS |
| **Статус поддержки** | Активно, золотой стандарт экосистемы React | Активно (Measured, v0.23, август 2026) | Нерегулярные обновления, стагнация | Активно |
| **Формат данных** | **Чистый структурированный JSON** | **Чистый структурированный JSON** | JSON | Неприемлемо (сырой HTML/CSS) |
| **Доступность (a11y)** | **Отличная** (встроенные KeyboardSensor, ARIA) | Базовая (сложная кастомизация a11y) | Слабая | Не соответствует WCAG AA |
| **Интеграция с дизайн-токенами** | **100% контроль** через Tailwind и Shadcn | Ограничена полями Puck | Сложная | Сложная |
| **Стоимость миграции** | **Минимальная** (библиотека уже установлена) | Высокая (полная замена верстки редактора) | Высокая | Критическая |

### 10.2. Решение
**Принято решение: Развивать собственный движок на базе уже установленного `@dnd-kit`.**  
*Обоснование:*
1. `@dnd-kit` уже установлен, протестирован в кодовой базе и не добавляет нового веса в бандл приложения.
2. Он обеспечивает 100% контроль над доступностью с клавиатуры и экранными дикторами (`aria-live`), что критично для соответствия закону ЗРУ-641 и стандарту WCAG 2.1 AA.
3. Он позволяет реализовать строгий расчет контрастности и жесткую привязку к дизайн-токенам без взлома закрытых внутренних интерфейсов внешних библиотек.
4. Сторонние редакторы (GrapesJS) категорически запрещены, так как сохраняют небезопасный сырой HTML и стили в обход дизайн-системы.

## 12. Поэтапный план реализации (Phased Slices)

Каждый рабочий этап завершается в полностью рабочем, протестированном и компилируемом состоянии:

### Этап B1: Модель данных Grid Layout V2 и адаптер совместимости
- Обновление `@college/shared`: типы `PageContentV2`, `PageSection`, `PageRow`, `PageCell`, `SectionStyleTokens`.
- Разработка и валидация адаптера `migratePageContentV1toV2()` (автоматическая миграция без потери данных).
- Серверная валидация структуры сетки в NestJS (`PagesService`).
- Unit-тесты на валидацию и миграцию всех существующих страниц.

### Этап B2: Визуальный WYSIWYG-холст и Инспектор свойств (Inspector Panel)
- Замена форм внутри карточек на визуальный рендеринг реальных компонентов на холсте в режиме редактирования (`isEditing: true`).
- Создание правой панели инспектора: выбор блока по клику, настройка контента на узбекском и русском языках.
- Реализация панели стилизации по дизайн-токенам (фон, отступы, ширина, скругления).
- Автоматический калькулятор контрастности WCAG AA с блокировкой недопустимых сочетаний.

### Этап B3: 12-колоночная сетка, Dnd-перетаскивание и Дерево структуры
- Реализация краевого определения зон падения (Left/Right $\to$ разделение колонок, Top/Bottom $\to$ перемещение внутри ячейки, Gutter $\to$ новый ряд).
- Интерактивный сплиттер изменения ширины колонок мышью и кнопками доступности.
- Боковое дерево структуры (Outline / Navigator): древовидный обзор блоков, скрытие, удаление и быстрый переход.
- Встроенный переключатель адаптивного предпросмотра (Desktop / Tablet / Mobile).

### Этап B4: Расширенная библиотека академических блоков и шаблоны
- Реализация 10 новых блоков (Hero, Stats counter, Timeline, Tabs, Image Carousel с кнопкой паузы, Banner, Quote, Anchor Nav и др.).
- Модальное окно выбора из 5 академических шаблонов при создании страницы.
- Механизм сохранения блоков в шаблоны (Reusable Blocks / Patterns).
- Обновление онбординг-тура для администраторов по возможностям нового визуального билдера.

## 13. Открытые вопросы для согласования

1. **Режим изоляции холста (Canvas Frame)**:
   - *Вариант А (Рекомендуемый)*: Холст рендерится внутри встроенного адаптивного контейнера с CSS-переменными темы. Быстрее работает, не требует накладных расходов на iframe, плавно масштабируется при переключении Desktop/Tablet/Mobile.
   - *Вариант Б*: Холст рендерится в изолированном `<iframe>`. Обеспечивает 100% изоляцию CSS от стилей админки, но усложняет передачу контекста аутентификации и drag-and-drop событий.
2. **Шаблоны при создании страницы**:
   - Показывать ли диалог выбора готового шаблона (Пустая страница / Главная / О техникуме / Приемная комиссия / Кафедра / Контакты) сразу при нажатии кнопки «Создать страницу»?
3. **Повторно используемые блоки (Reusable Blocks)**:
   - Сохранять ли блоки как независимые копии (изменение блока на странице А не затрагивает страницу Б) или поддержать также глобальные синхронизируемые мастер-блоки (Global Blocks)?
